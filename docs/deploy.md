# Deploying the public demo

The demo runs on two free tiers: a **Render** web service, which builds the `Dockerfile`, and a **Neon** Postgres database. Neither needs a credit card. It takes about 15 minutes.

```
browser ──https──▶ Render (free, Docker)                              Neon (free Postgres)
                   uvicorn: React console + API + job worker ──────▶  orders, messages, photos, job queue,
                   + the mock ERP, called over loopback               audit log, LISTEN/NOTIFY for live updates
                                │
                                └──▶ Anthropic API (optional: without a key, parsing uses the fuzzy fallback)
```

## What the free tiers mean for the demo

| | Limit | What visitors notice |
|---|---|---|
| Render free web service | Spins down after 15 minutes with no inbound traffic; about a minute to wake. 750 instance hours a month per workspace. | The first visit after a quiet spell waits about a minute. |
| Neon free | 100 CU-hours a month per project, 1 GB storage, scales to zero after 5 minutes idle. | The first query after a pause takes about a second longer. |
| Anthropic | Pay as you go. The app stops calling the model once it has spent `LLM_DAILY_BUDGET_USD` (default $0.50) in a UTC day. | After that, drafts are made by fuzzy matching and say so in a note. |

The app's job worker polls Postgres, so Neon stays awake whenever Render does. A browser tab that is hidden closes its live-update stream, so a forgotten tab doesn't keep both running.

Limits checked on 5 October 2026: [Render free](https://render.com/docs/free) and [Neon free plan](https://neon.com/faqs/free-plan-limits-and-quotas).

## 1. Create the database on Neon

1. Sign up at [neon.com](https://neon.com) with GitHub.
2. Create a project called `orderdesk`:
   - **Region:** AWS Europe Central 1 (Frankfurt). It's the closest to Dubai that is also a Render free region.
   - **Postgres version:** 16, to match CI.
3. On the project dashboard, choose **Connect**. Turn **Connection pooling off** and copy the connection string. It looks like `postgresql://neondb_owner:…@ep-…eu-central-1.aws.neon.tech/neondb?sslmode=require`.

   **Use the direct string, not the `-pooler` one.** Live updates use `LISTEN`, which PgBouncer in transaction mode doesn't support. With the pooled URL, orders still work but the console stops updating by itself.
4. Optional: under **Branches → main → Compute**, set the maximum size to 0.25 CU. The demo needs no more, and the monthly hours last longer.

Don't create any tables. The container runs the migrations and seeds the demo data on its first start.

## 2. Make an Anthropic key just for the demo

In the [Anthropic Console](https://console.anthropic.com):

1. Create a workspace called `orderdesk-demo`.
2. Set a monthly spend limit on it (for example $10).
3. Create an API key in that workspace.

The app's daily budget is the first guard and the workspace limit is the backstop. A Sonnet draft costs about 2 cents (see `docs/results/eval.md`), so $0.50 a day covers roughly 25 visitor orders.

Paste the key only into Render (next step). It never goes in the repo or in chat.

## 3. Deploy on Render

1. Sign up at [render.com](https://render.com) with GitHub and give it access to `azb27/orderdesk`.
2. Choose **New → Blueprint** and pick the repo. Render reads `render.yaml` and proposes one free web service called `orderdesk` in Frankfurt.
3. It asks for the two secrets marked `sync: false`:
   - `DATABASE_URL`: the Neon direct connection string from step 1.
   - `ANTHROPIC_API_KEY`: the key from step 2. Leave it empty to run the demo without a model.

   `SECRET_KEY` and `WHATSAPP_APP_SECRET` are generated by Render.
4. Choose **Apply**. The first build takes about 5 minutes. The service then logs:
   - the migrations being applied;
   - `{'products': 211, 'customers': 180, …}`, which is the seed;
   - `Uvicorn running`.

   Later restarts print `already seeded` instead.

## 4. Check it works

1. Open `https://<service>.onrender.com/healthz`. You should see `"ok": true`, and `"llm": true` if you gave it a key.
2. Open the site and sign in with **Maria (order-taker)**.
3. Open the phone (top right). Send a sample order, or a photo of the handwritten list.
4. In a few seconds a draft appears in **To check**.
5. Confirm it. The stamp lands, the order moves to **In ERP**, and the phone gets a reply in the retailer's language.

If the live dot in the top bar stays grey, `DATABASE_URL` is the pooled string. Swap it for the direct one.

## Running it

**Demo data.** Visitors' orders and conversations are deleted at start-up once they are older than `DEMO_RETENTION_DAYS` (3). The seeded history is kept. Because the service spins down when idle, this runs often.

**Full reset.** In Neon's SQL editor, run the following and then choose **Manual Deploy → Restart** on Render:

```sql
DROP SCHEMA erp CASCADE;
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
```

**Rotating secrets.** Changing `SECRET_KEY` signs everyone out. Changing `WHATSAPP_APP_SECRET` affects nothing a visitor can see, because the simulator signs with whatever the server holds.

**Model and budget.** These are environment variables (`ORDERDESK_MODEL`, `LLM_DAILY_BUDGET_USD`). Changing one restarts the service, with no rebuild.

**Building locally.**

```bash
docker build -t orderdesk-demo .
docker run --rm -p 8000:8000 -e DATABASE_URL=postgresql://… -e SECRET_KEY=dev -e COOKIE_SECURE=0 orderdesk-demo
```

Behind a proxy that re-signs TLS, pass its CA bundle as a build secret: `--secret id=ca,src=/path/to/ca.crt`. It's used during the build only and never lands in an image layer.

## What the demo leaves out, and what production would add

| Demo | Production at Saffron Lane |
|---|---|
| A phone simulator posts signed webhooks to the app. | Meta's WhatsApp Cloud API posts to the same `/webhooks/whatsapp` route. `channels/whatsapp.Sender` gets its cloud mode, a stub today, to send the templated replies through the Graph API. |
| A mock ERP on the same server, reached over loopback (other callers get 403). | The distributor's ERP API, with the same idempotency key per order. |
| One process: API, job worker and live updates. | API and worker as separate services on the same Postgres queue. Workers scale with `SKIP LOCKED`. |
| Photos stored in Postgres. | Object storage with a retention policy. The `media` table keeps only the key. |
| Free-tier Postgres that sleeps. | A paid instance with point-in-time recovery, since orders are financial records. |
| Two demo users with a published password. | Single sign-on, and the order-taker and supervisor roles from the directory. |
