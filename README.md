# Orderdesk

**Retailers in the Gulf order stock over WhatsApp: a text in English, Arabic, Arabizi or Roman Urdu, a photo of a handwritten list, or "same as last week but no milk". Orderdesk reads those messages and drafts a sales order. Each line is matched to the catalogue with its evidence, and the customer's prices, stock and credit are filled in. An order-taker confirms or fixes the draft in a keyboard-first console. The order then posts to the ERP, and the retailer gets a reply in their own language.**

## What the eval says

On 300 generated test conversations (1,902 order lines, four language styles, 42 photos), scored line by line against ground truth with no LLM judge:

- **Claude Sonnet 5 finds 93.5% of order lines exactly** (right product *and* right quantity) and gets **72.7% of orders exactly right**. Fuzzy matching with no model, which is also the fallback when the API is down, gets 56.4% and 20.7%.
- **The customer's own history matters more than the model.** Without order history and nicknames, Sonnet drops to 56.2% of lines on the same 100 conversations (92.5% with them). Swapping Sonnet for Haiku 4.5 costs 4.6 points.
- **Photos of handwritten lists:** 88.2% of lines found. **Names the parser was never given:** 88.7%.
- **A hand-written set** of 40 conversations that didn't come from the generator is harder: 80.5% of lines found, 60.0% of orders exactly right. Most of the gap is one thing the generator never modelled: whether "4 boxes" means 4 cartons or 4 of a product sold by the box. It is written up, and deliberately left for real messages to settle.
- **Nothing auto-confirms.** At a 2% line-error budget the confidence model would let 85% of lines skip a look. But none of the whole-order thresholds in the report gets under the rollout plan's 1% gate. Every order is confirmed by a person; the [rollout plan](docs/engagement/rollout-plan.md) says what evidence would change that.

| Configuration (test split) | Lines found | Lines correct | Orders exactly right | $ / conversation |
|---|---|---|---|---:|
| Fuzzy matching, no model | 56.4% [52.0, 60.8] | 72.2% [69.0, 75.3] | 20.7% [16.0, 25.3] | $0 |
| Claude Haiku 4.5 | 88.9% [86.7, 90.9] | 91.3% [89.6, 92.9] | 57.0% [51.3, 62.7] | $0.0118 |

That report also has the slices, ablations, McNemar tests, touchless rates, and the before-and-after of the fixes the failure analysis led to.*

## How it reads an order

```
WhatsApp (Cloud API webhook, HMAC-verified, idempotent on message id)
   │
   ▼  Postgres job queue (FOR UPDATE SKIP LOCKED, backoff, dead letter)
1. extract    model, forced tool call   what the customer wrote: product words, size, quantity, unit, add/remove/set
2. retrieve   code                      candidate SKUs: aliases, fuzzy match, the customer's history and nicknames
3. resolve    model, ids enumerated     one candidate per line, or NONE; anything else is rejected, not repaired
4. build      code                      units, contract prices in integer fils, stock, substitutes, credit, flags
5. confidence code                      a logistic model over the evidence, fitted on dev, reported on test
   │
   ▼  live to the console (LISTEN/NOTIFY → server-sent events)
order-taker confirms ─► ERP post (idempotency key, retries) ─► templated reply in the retailer's language
```

**The model never produces an id, a price, a unit conversion or a total** ([ADR 0001](docs/adr/0001-the-model-chooses-from-candidates.md)). It reads, and it chooses from a list it was given. Everything with a number in it is computed in code, so every figure on the order pad can be traced. Code also covers what the model is unreliable at:

- If the customer wrote no size and has only ever bought one size, code uses that size.
- A quantity far outside the customer's history is flagged for a look.
- A removal can only drop something that is on the order.

## The product

- **Console** (React 19, TypeScript strict, hand-written CSS with design tokens; no UI kit):
  - an inbox by status;
  - the conversation with the words behind the selected line highlighted, Arabic right to left;
  - an order pad showing confidence, flags and evidence per line;
  - one-click alternatives and substitutes, and product search by name, Arabic name or barcode;
  - "teach this name" after a correction;
  - a credit bar, and keyboard flow (j/k, arrows, e, Enter);
  - a rubber stamp when it posts.
- **Phone simulator** that sends real, signed Cloud API payloads to the same webhook, with samples in each language style and two handwritten-list photos.
- **Back end** (FastAPI, SQLAlchemy 2, Alembic, Postgres 16; [ADR 0002](docs/adr/0002-postgres-is-the-only-state.md)):
  - Postgres is the only state: the queue, live updates and photos all live there;
  - message sessions (a retailer's messages within 15 minutes amend one draft);
  - roles, so held and high-value orders need a supervisor;
  - an audit log of every edit and decision;
  - a mock ERP with fault injection (fail, lose the response, slow, reject). Tests show a lost response and its retry still book the order once.
- **Demo guards:** a daily model budget with fallback to fuzzy matching, a per-IP rate limit, the mock ERP answering loopback only, and visitor data cleared after three days.
- **Tests:**
  - pytest against real Postgres (51 tests);
  - Vitest (14 tests);
  - Playwright end-to-end against the same Docker image that deploys (phone → draft → confirm → ERP → reply).

  All run in CI.

## Run it

```bash
make setup     # Python deps, npm ci, a local Postgres 16 on port 5433
make world     # regenerate catalogue, customers, history and eval sets (deterministic; the outputs are committed)
make test      # pytest + vitest
make dev       # API on :8000 with the worker, Vite on :5173; sign in with a demo button
```

Without `ANTHROPIC_API_KEY`, orders are read by the fuzzy fallback, and the draft says so. With a key, put it in an untracked env file and keep `LLM_DAILY_BUDGET_USD` low. To reproduce the eval: `cd api && python -m evals.run --config sonnet --split test` (about $6.40, resumable, cached), then `python -m evals.report`.

Deployment: `docker build -t orderdesk-demo .`, and [docs/deploy.md](docs/deploy.md) for Render plus Neon on free tiers ([ADR 0005](docs/adr/0005-free-tier-deploy.md)).

## Layout

```
api/src/orderdesk/   world/ (generator)  parse/ (extract, retrieve, resolve, build, confidence, fuzzy)
                     channels/ (WhatsApp webhook, replies)  jobs/ (queue)  erp/ (client, mock)  db/  web/ (FastAPI)  desk.py
api/evals/           run, score, report, failures, calibrate        api/tests/
web/                 React console and phone simulator; Playwright in web/e2e/
data/                world/ (catalogue, customers, history), eval/ (messages, images; truth/ is read by evals only), model/
docs/                engagement/, adr/, results/ (generated), deploy.md
```

## What's real and what isn't

The customer, its catalogue, customers and messages are generated by `orderdesk.world.build`. The street names for products come from a lexicon, and 29% of it is held out of the parser's alias table to measure names it has never seen. The 40-conversation hand-written set is the check on the generator. The discovery memo's figures are labelled "(brief)": they are the fictional client's claims, not measurements. Every result in `docs/results/` comes from a stored run, with the command that made it written above it.
