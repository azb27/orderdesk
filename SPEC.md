# Orderdesk: build spec

> Retailers in the Gulf order stock by WhatsApp: a text in English, Arabic, Arabizi or roman Urdu, a photo of a handwritten list, or "same as last week but 2 more Pepsi". At a distributor, a team retypes those messages into the ERP before the afternoon cut-off. Orderdesk reads the messages, matches every line to a catalogue SKU with evidence, builds a draft sales order with the customer's prices, stock and credit, and puts it in front of an order-taker who confirms it in one keystroke or fixes it. Confirmed orders post to the ERP, and the retailer gets a confirmation in their own language.

**Thesis this project proves:** *I can run a forward-deployed engagement end to end: find the workflow, build the integration, the model pipeline and the screen people use all day, measure it, and roll it out safely.*

**Target reader:** a hiring manager for Forward Deployed Engineer or AI solutions roles (Gulf and global). 90 seconds on the README and the demo GIF, then 5 minutes clicking around the live demo, then the eval and the engagement documents.

**What it adds to the portfolio:** Stockroom showed data work and an agent; Skeptic showed evaluation discipline. Orderdesk shows the rest of the FDE job: a production web app (React + TypeScript + hand-written CSS), an integration that follows a real API contract (WhatsApp Cloud API webhooks), Postgres, background jobs, auth and roles, an audit trail, end-to-end browser tests and a live deployment.

## 1. The customer (fictional)

**Saffron Lane Foodstuff Trading LLC**, a Dubai FMCG distributor (warehouse in Al Quoz) supplying ~180 baqalas, cafeterias and small restaurants across Dubai and Sharjah. The engagement brief (`docs/engagement/discovery-memo.md`) is fiction written to be plausible. Every number in it is labelled as a *brief* figure, never a result.

- Orders arrive on two WhatsApp Business numbers. Five order-takers retype them into the ERP before the 16:00 cut-off for next-day delivery.
- Messages are in English, Arabic, Arabizi ("3 kartoon pepsi"), roman Urdu/Hindi ("pepsi ki 2 peti"), or mixed. Some are photos of handwritten lists. Shops use their own names for products ("the red Al Safi", "small water").
- Errors that cost money: wrong pack size (piece vs carton), wrong variant (diet vs regular), missed lines in long lists, orders placed for customers over their credit limit.

## 2. Architecture

```
 Retailer (WhatsApp, or the demo phone simulator)
        │  Cloud API-shaped webhook: X-Hub-Signature-256 verified, idempotent on message id
        ▼
 FastAPI ── messages ── Postgres job queue (SKIP LOCKED) ── worker
                                                   │
           understand:  1. extract mentions + intent      (LLM, structured output)
                        2. retrieve SKU candidates        (deterministic: aliases, fuzzy, customer history)
                        3. resolve each mention           (LLM, choice constrained to candidate ids or NONE)
                        4. build the draft order          (deterministic: units, price list, stock, credit)
                        5. score confidence per line      (features → calibrated probability)
                                                   │
        React console (rep / supervisor) ◄── SSE (LISTEN/NOTIFY) ──┘
           inbox · draft editor · SKU search · evidence · keyboard-first · RTL
                │ confirm
                ▼
        ERP adapter (mock ERP API: idempotency key, retries, dead letter)  →  WhatsApp reply (template, retailer's language)
```

- **The LLM never produces an id, a price or a total.** It extracts what the customer said and chooses among candidate ids it was given. Prices, units, stock and credit are computed in code.
- **Evidence for every line:** the text span (or image region description) it came from, the candidates considered, why this one won.
- **Nothing reaches the ERP without a human** in v1. The rollout plan (P7) describes when auto-confirm would be safe and what the eval says about it.

## 3. Data (synthetic, generated by script)

| Table | Content |
|---|---|
| catalogue | 211 SKUs in 83 product families: beverages, water, dairy, eggs, bread, snacks, rice and staples, oil and tea, canned food, cleaning, tissue. Fictional brands. Pack hierarchy (piece → pack → carton), EAN-13 barcodes, Arabic names |
| customers | ~180 retailers: type, area, language mix, phone, price list, credit limit and balance, nicknames they use |
| price lists | Base list + customer-tier discounts + a few customer-specific contract prices |
| stock | On-hand per SKU with some zero-stock lines (substitution logic) |
| order history | 12 weeks of past orders per customer ("the usual", "same as last week") |
| messages | Generated orders rendered as WhatsApp messages with ground truth (below) |

**Ground truth and the generator.** Each eval message comes from a known order (customer, lines, quantities, units). It is rendered in one of the language styles with realistic noise: typos, abbreviations, missing units, unit words in four languages, emoji, line breaks, voice-of-shopkeeper phrasing, amendments ("add 2 more", "cancel the milk"), references to history ("the usual"), and handwritten-list images (rendered with handwriting fonts, rotation, blur, lighting).

**Circularity guard.** The generator draws product names from a *street-name lexicon*. Only part of it is in the catalogue's alias table the parser can see; the rest is held out. Results are reported separately for seen and unseen street names. A further ~40 messages are hand-written (not from the generator) and reported as their own set.

## 4. Evaluation (the headline)

Scoring is deterministic against ground truth; no LLM judge.

| Metric | Definition |
|---|---|
| Line F1 | A predicted line matches a true line when SKU and base-unit quantity both match |
| Order exact | Every line right, nothing extra, nothing missing |
| Money at risk | AED value of wrong, missed or extra lines (customer price list) |
| Touchless rate at k% error | Share of lines the confidence policy would auto-accept while keeping the error rate among them ≤ k% |
| Cost and latency | $ per message, p50/p95 seconds |

**Configurations:** fuzzy-match baseline (no LLM); Haiku 4.5 pipeline; Sonnet 5 pipeline; ablations without customer history and without retrieval (whole catalogue in the prompt). Every rate has a bootstrap CI; pairwise differences use McNemar. Slices: language style, text vs image, seen vs unseen names, message length.

## 5. Product requirements

- **Webhook** follows the WhatsApp Cloud API contract: GET verification handshake, POST with `X-Hub-Signature-256` HMAC check, `entry[].changes[].value.messages[]` parsing, idempotency on the message id, media fetched through an adapter. The demo's phone simulator calls the same endpoint with signed payloads. Switching to Meta is configuration (documented, not done).
- **Jobs:** Postgres-backed queue (`FOR UPDATE SKIP LOCKED`), retries with backoff, a dead-letter state visible in the console. No Redis.
- **Order sessions:** messages from one retailer within 15 minutes amend the same draft until it's confirmed.
- **Console (React + TypeScript + CSS):** inbox by urgency and cut-off; conversation view with original message (Arabic rendered right-to-left) beside the draft; line editor with SKU combobox, unit and quantity; confidence and evidence per line; substitutions for out-of-stock lines; credit-limit hold; keyboard shortcuts (j/k, enter to confirm, e to edit); live updates over SSE; responsive down to tablet; WCAG AA contrast, focus states, screen-reader labels.
- **Roles:** order-taker confirms orders within credit; supervisor releases credit holds and orders above a value threshold. Every action lands in an audit log with who, what, before and after.
- **ERP adapter:** posts confirmed orders to a mock ERP service with an idempotency key; retries on 5xx and timeouts; never double-posts (tested by fault injection).
- **Replies:** confirmation message to the retailer in their language (template-based, never free-form LLM text to customers in v1).

## 6. Stack

Python 3.11, FastAPI, SQLAlchemy 2 + Alembic, Postgres 16, psycopg 3, rapidfuzz, Anthropic API · React 19, TypeScript, Vite, TanStack Query, plain CSS with design tokens (no UI kit) · pytest, Vitest + Testing Library, Playwright · Docker, GitHub Actions · free-tier hosting (decided in P6, with prices checked at the time).

    - **Jobs:** a Postgres job queue (`SKIP LOCKED`, exponential backoff, dead letter, supervisor retry).

## 8. Out of scope (v1)

- Voice notes (would need speech-to-text; the console shows them as "listen and key manually").
- A real WhatsApp Business account, real ERP, real customers or brands.
- Free-form LLM replies to customers; payments; delivery routing.
- Auto-confirming orders without a human. The eval says how close it is; the rollout plan says what would have to be true.

## 9. Honesty rules

- Brief figures (orders per day, minutes per order, error rates today) are fiction and labelled as such everywhere they appear.
- Results tables are generated by scripts from stored runs, with the command written above them.
- The eval is synthetic. Seen/unseen names and the hand-written set exist so the README can say how much of the score is the generator talking to itself.
